# V0.4 Roadmap And Evaluation

## 1. 为什么下一步不是继续堆功能

当前项目已经具备患者端聊天、家属端事件、熟悉素材、回忆页面、聊天记录、模型状态和测试结果页面。再继续增加大量新页面或分散功能，短期内并不会显著提升照护价值，反而会让系统更难验证、更难维护，也更难判断哪些模块真的在帮助患者和家属。

因此，v0.4 的重点不是“再加更多功能入口”，而是把已经存在的关键链路做得更闭环、更可信：

1. 提醒不只存在于列表中，而要有完成状态。
2. 回复不只停留在文字里，而要能准备好更自然的语音朗读。
3. 系统价值不只靠主观感觉，而要通过对照评估说明为什么它比普通 LLM 聊天更适合阿尔兹海默症照护。

## 2. 提醒完成状态为什么重要

阿尔兹海默症照护里的很多风险，不是“回答得像不像人”，而是“系统会不会把不该猜的事情猜成事实”。用药状态是最典型的例子。

如果患者问“我是不是还没吃药？”，普通聊天模型可能会顺着语气编出“已经吃过了”或“还没吃”，这会直接影响安全。提醒完成状态的价值在于：

- 把“是否完成”从自然语言猜测变成结构化记录。
- 让家属端可以看到已确认、待确认、未完成、跳过的差异。
- 让患者端在高风险问题上优先引用 reminder 数据，而不是引用模型幻觉。
- 让后续 caregiver event、提醒补录、家属确认动作形成闭环。

这也是为什么 v0.4 里“用药状态必须来自 reminder 数据”，而不是来自 LLM 的自由发挥。

## 3. MiniMax TTS 的作用

患者端对话如果只停留在文字层，仍然会受限于阅读能力、疲劳程度和当下情绪状态。TTS 的作用不是“增加一个炫技语音功能”，而是让最终的患者回复更容易被接收：

- 对不愿意盯着屏幕看的老人更友好。
- 在焦虑、傍晚不安或重复提问时，语音更容易形成陪伴感。
- 后续可与家属语音留言、熟悉老歌、回忆陪伴素材形成更自然的播放链路。

当前阶段选择 MiniMax TTS 的最小接入，是为了先把接口和 fallback 路径打通：

- 成功时：返回受控生成的音频地址。
- 失败时：明确 fallback 到浏览器 `speechSynthesis`。

这样系统不会因为第三方 TTS 状态不稳定而失去可用性。

## 4. 对照评估如何证明系统价值

“普通 DeepSeek 也能聊天”这件事本身并不奇怪。真正需要证明的是：在阿尔兹海默症照护场景里，为什么完整系统比直接问 LLM 更合适。

对照评估把两条链路拆开比较：

1. `baseline_direct_llm`
   - 只把用户问题直接发给 DeepSeek
   - 不带患者档案、熟悉素材、提醒状态、安全模板、家属事件

2. `care_system`
   - 走当前完整链路
   - 包括 profile、materials、history、reminder status、safety guard、template fallback、caregiver events

评估指标包括：

- 是否短句
- 是否温和
- 是否无责备
- 是否避免用药幻觉
- 是否避免对已故亲人进行直接刺激性纠正
- 是否避免鼓励独自外出
- 是否使用 profile 或熟悉素材
- 是否能触发家属事件
- 是否给出简单下一步

当前结果显示：完整照护系统平均分显著高于普通 LLM 直连。这说明系统价值不只来自“模型回答能力”，更来自上下文组织、安全约束和家属反馈闭环。

## 5. 当前仍然不是医疗系统

这个项目当前是照护辅助系统原型，不是医疗系统，也不能替代医生、护士或家属。

必须持续保持以下边界：

- 不能做医学诊断。
- 不能承诺患者已经吃药，除非 reminder 状态明确。
- 不能让患者自己做高风险决定，例如独自外出或自行补药。
- 不能把已故亲人的事实以刺激性方式直接砸给患者。
- 不能把 TTS、聊天和回忆陪伴包装成正式医疗干预。

更准确的定位是：

它是一个围绕阿尔兹海默症家庭场景设计的“受控聊天 + 资料辅助 + 家属反馈 + 风险提示”系统原型，目标是帮助家庭照护更稳定，而不是代替家庭照护本身。
